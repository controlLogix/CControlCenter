The implementation uses the already registered Transactional Client (FED-02), Idempotent Receiver (FED-04), Competing Consumers (FED-06), Message Filter (FED-07), Canonical Data Model (FED-10) and Correlation Identifier (FED-16). Their registry history remains preserved. The simpler alternative was to keep direct execution on receipt and check only the final result; that cannot prevent another receiver executing after an acknowledgment loss. The added claim/grant exchange costs a network round trip and requires the origin to be reachable for a new reservation. An already granted receiver can continue offline, and its result remains durable for reconnect. There is no timeout-based reassignment of accepted work.

These changes repair the current SQLite-backed implementation behind its existing store/plugin boundaries. They add no new shared SQL authority or non-NATS network channel. STATE-01's later NATS storage migration remains required and must preserve the same ownership and commit invariants. The fixed boot kernel and broader plugin redesign remain future phases.

## Work contract and compatibility

Messages, handoffs, knowledge, code and control retain envelope v2. Work, reservation requests (`work_claim`), grants (`work_grant`) and results use v3. New work is published to `am.work.<peer>.<rid>.<role>.v3` with `work3_<peer>_<rid>_<role>` consumers. Existing exact-filter v2 work consumers cannot consume those offers. Requests, grants and results use the existing durable message stream; per-node inboxes prevent an old node from consuming another node's copy.

An incoming item is visible as blocked with reason `awaiting origin grant`; approval alone does not make it immediately claimable. One origin-owned transaction selects an executor and records its grant. Only a matching grant changes the receiver's item to ready. Another contender is cancelled. Replayed or delayed grants cannot revive cancelled work, and a local-origin redelivery cannot override a remote reservation.

The offer digest binds the immutable requested work and repository identity. The result digest binds returned terminal state and text. These digests detect mismatched records; they are not signatures, proof of semantic correctness or validation of arbitrary external artifact bytes. This incremental protocol retains the existing automatic terminal-result behavior after identity validation. The original AMX-BASE-005 repair wording also calls for repository-version and artifact evidence. This repair binds the immutable offered task and repository ID plus returned text; it does not qualify a checked-out commit or external artifact bytes. Those broader product requirements remain explicitly open under P05-AC01/P05-AC03/P05-AC05 and P10-AC03; FAIL-16 and FAIL-19 are not marked fully passed by this repair. No original acceptance criterion is removed. The peer's credential is the authenticated boundary; node IDs distinguish that peer's processes but do not create separate security principals within a peer.

## Upgrade and recovery

1. Back up each existing hub and stop admitting old-protocol work. Record pending, accepted and uncertain old delegations before upgrading. Complete or explicitly reconcile them; do not simply redispatch an uncertain task.
2. Upgrade the participating hubs. Store migration 5 makes its existing pre-migration backup, adds a trigger and preserves prior tables/data. New offers use the isolated v3 subject suffix. Unupgraded receivers cannot execute new work; do not treat their presence as protocol readiness.
3. Old incoming work/results remain in quarantine for reconciliation. Approving a v2 item does not bypass v3 binding requirements. Existing terminal rows receive a durable pending marker, but rows without a verifiable grant are not automatically resent as trusted v3 results. Inspect their preserved records and reconcile explicitly.
4. Do not roll older software back over a database containing active v3 work: it cannot honor the new grant boundary. Stop/drain, preserve both stores/outboxes and reconcile reservations first. Restoring an older backup cannot itself prove that a receiver stopped executing.

Backup destinations must support local filesystem hard links. Failure to publish leaves the previous completed snapshot intact. File-content flushing and SQLite restore tests are exercised; this is not a new power-loss, disk-loss or replicated-storage guarantee. Persistent test evidence identifies the actual fault model.
