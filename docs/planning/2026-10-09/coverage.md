## Approved storage direction — NATS shared persistence

Ryan approved **NATS JetStream as the preferred shared persistence layer** after the original coverage was prepared. This current decision takes precedence over older storage alternatives and SQL-authoritative suggestions in the research. The historical baseline and all 132 original `sourceProposal` objects remain unchanged. The approval establishes a direction; implementation choices and release evidence still require the phase gates.

Authoritative domain owners validate commands and persist shared records through scoped NATS contracts. Streams retain task/run/delegation history, intent, reservations, acceptance and evidence references. KV supplies current views, configuration, capability advertisements and suitable bounded state. Object Store holds large artifacts using immutable version/digest identities. SQL may support queries, joins and reporting as an **optional rebuildable view**; it does not become another shared writer or command authority.

This uses the persistence facilities of the required communication backbone while preserving explicit ownership. It does not give every plugin or connected hub permission to mutate shared objects. It adds no external kernel write interface and does not move provider secrets into ordinary shared records.

KV has per-key conditional updates, but its default one-revision history and 64-revision maximum are insufficient as the complete task ledger. Object Store same-name replacement likewise does not retain an artifact’s version history automatically. Preserve authoritative history in retained Streams, bind artifacts by immutable identity, and test interruption between artifact upload and record publication. [KV revisions](https://docs.nats.io/learn/key-value/history-and-revisions), [Object Store replacement](https://docs.nats.io/learn/object-store/under-the-hood).

Atomic batch publishing is available from server 2.12, with batch deduplication from 2.12.1. It can commit related messages or underlying KV-subject writes **inside one stream**, subject to supported expected-sequence checks. It does not create a transaction across different streams/buckets, hubs or external tools. Pin and test server/client versions, unknown commit outcomes and recovery. [Atomic batch documentation](https://docs.nats.io/learn/jetstream/advanced-publishing), [versioned batch specification](https://github.com/nats-io/nats-architecture-and-design/blob/main/adr/ADR-50.md).

Direct multi-subject point-in-time reads were added in 2.11, provided sufficient history remains and the snapshot/pagination contract is used. Independent KV reads do not automatically form that snapshot. Direct reads can also lag the leader; current command decisions need authoritative revision checks and the appropriate read path. [Snapshot contract](https://github.com/nats-io/nats-architecture-and-design/blob/main/adr/ADR-31.md), [read freshness](https://docs.nats.io/learn/jetstream/get-direct).

Use retention deliberately: consumer acknowledgment or a durable consumer position is not permanent task history. WorkQueue and Interest retention remove records according to consumer acknowledgment/interest. Independent hubs need explicit persistence domains and scoped sharing. Mirrors/sources copy records asynchronously; they do not provide unrestricted all-hub mutation, and source records can expire before replication. Accepted and acceptance-unknown work remains reserved until explicit reconciliation. [Retention](https://docs.nats.io/learn/jetstream/retention-policies), [leaf domains](https://docs.nats.io/learn/topologies/leaf-nodes), [mirroring](https://docs.nats.io/learn/jetstream/mirrors-and-sources), [retention gaps](https://github.com/nats-io/nats-architecture-and-design/blob/main/adr/ADR-59.md).

## Evaluation method and reusable gates


1. Declare the decision, normal deterministic alternative, data scope, owner, unknown/fallback outcomes and measurable target before implementation or spending.

2. Keep schema/failure/permission tests separate from live semantic accuracy, host behavior, hardware behavior and commercial-provider qualification. Prior synthetic examples establish no production accuracy.

3. Use representative reviewed positives, hard negatives, none-of-the-above, source/version conflicts, counterevidence and adversarial material. Separate tuning, validation and untouched release sets; prevent label or answer leakage.

4. Compare ordinary workflow, tools-only and tools-plus-skill using comparable inputs and accepted outcomes. Report class errors, high-confidence errors, coverage/abstention, critical-evidence recall and required-obligation retention.

5. Record actual Jev plus downstream usage, failed attempts, retries, cache pricing, queue/network time, source expansion and rework. Unknown billing stays unknown. Overlapping records do not yield additive savings.

6. Run trigger and near-miss tests across the whole skill suite and behavioral tests on every claimed host/version. P09 local qualification of 12 skills does not qualify remote modes of the three P10 skills.

7. Run required deterministic authority, durability and federation failure fixtures regardless of whether optional semantic decisions are enabled. Capability advertisements, typed facts and model confidence confer no permission.

8. Enable each evaluated capability explicitly by scope/version. Retain a disable/fallback/rollback path and a reviewed revise/defer/alternative outcome for unsuccessful candidates; never silently erase catalog coverage.
