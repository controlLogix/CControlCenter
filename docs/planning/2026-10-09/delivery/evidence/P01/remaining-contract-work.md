# Remaining P01 executable contract work

Reviewed base: `421d18b26227cb1233e362627fc7de75064ea3b0`, plus the current uncommitted ten payload schemas and `contracts/v1/registry.json` supplied during this review. This is a bounded source audit for P01-T01/T03, not phase acceptance. No implementation or task status was changed.

## What is implemented

The promoted eight schema files define seven infrastructure objects plus shared definitions. Python and TypeScript independently implement strict parsing, JCS bytes/digests, Ed25519 signing/verification and signed outer-envelope binding. `tests/contracts/test_conformance.py` exercises infrastructure shapes, strict bytes, bilateral signatures and tampering. Those tests do not execute lifecycle, task, delegation, attempt or effect transitions.

The parent has now added ten closed payload schemas: task-inspect, task-reserve, delegation-offer, delegation-decision, execution-report, cancellation-request, delivery-receipt, plugin-lifecycle, operation-outcome and status-query. The new local registry binds ID, major, message kind, schema and destination service. This removes the earlier absence of named payload definitions, but neither SDK currently reads that registry. `verifyEnvelope` validates only the infrastructure envelope/attestation and returns claims; it does not select a payload schema by contract ID. The separate `validate` operation can validate a named payload when explicitly invoked, but callers can currently omit that step.

The accepted P00 models remain only in `delivery/contracts/state-machines.json`: plugin (14 transitions), task (13), delegation (18), attempt (14), effect (9), totaling 68. The draft verifier checks table edges against fixture-provided role/guard strings. No corresponding model file, transition evaluator or state schema is present in promoted `contracts/v1` or either SDK.

## Direct schema-only probes

Using the prepared WSL Python SDK against current schemas, the following values were accepted by `validate`:

- A plugin dependency whose packageId equals its own packageId, with otherwise valid minimumVersion/exclusiveMaximumVersion/optional fields.
- A plugin-context effectiveGrant.subjectInstanceId different from the context instanceId.
- An owner-record with outcome=rejected while retaining the example's one effect.
- A message-envelope with an unregistered contractId and arbitrary object payload.

These are expected examples of the current shape-only boundary, not claims that deployed production authorization is bypassed. The first self-dependency probe used a mistaken `required` field and was rejected; correcting it to the real schema's `optional` field exposed the intended semantic gap. Python and TypeScript both visibly use generic schema validation; the probes above were executed only in Python. No request bodies or credentials were stored.

## Review of the ten new payloads

- `operation-outcome`: require an explicit reconciliation policy or document a constrained retryable meaning. Unknown plus retryable must not mean a new operation or prove no side effect. Bind payload operationId to the operation being answered; do not confuse the reply envelope's own delivery identity with that target identity.
- `delivery-receipt`: originalMessageId provides a lookup key, but the owner must bind it to the recorded operation and delivery target. A signed receipt from an unrelated source must not acknowledge another delivery. receivedAt needs actual calendar validation, not the timestamp regex alone.
- `plugin-lifecycle`: generation and observedAt are useful observations, but a stale generation cannot change the current instance, and status=ready alone is not proof that readiness guards passed. The model must distinguish observation from authorized transition.
- `delegation-offer` and `task-reserve`: assignmentEpoch must be monotonic under the origin owner's current revision. Reusing a task/attempt with different grant, executor or repository revision is a conflict, not an idempotent replay. acceptBefore must not allow first acceptance after the deadline.
- `delegation-decision`: accepted_reserved requires the origin grant and committed receiver acceptance. approval_pending/rejected must not create execution authority. Preserve separate origin and receiving-owner records.
- `execution-report`: completion_reported is deliberately not accepted. Check source executor, attempt, grant, repository revision and actual artifact bytes at the owner. The schema's artifact metadata alone is not verification.
- `cancellation-request`: missing stop confirmation remains cancel_requested/unknown. It cannot be treated as immediate cancelled just because its message was acknowledged.
- `status-query`: includeHubs is only a request. The responding owner must filter connected hubs by current scope; the boolean never expands authorization. A typed status response is still needed before LOCAL-01 consumers depend on this contract.

## Follow-up during implementation

After this audit snapshot, the parent wired `validate_payload` / `validatePayload` and CLI `validatePayload` into both SDKs and full envelope verification. These now resolve the ten-entry registry, validate kind/major/destination and payload shape, bind non-null task/attempt IDs and delegation reference, and bind operation-outcome.operationId to correlationId. Cross-language payload tests are being added separately. These changes close part of the registry-admission gap, not the five model/replay/lifecycle gaps.

Payload execution grants and the request actor's authorization grant are different records. Do not enforce equality between them. Execution-grant validation must instead use the origin's reservation/executor record and the requested operation scope. This clarifies the cross-field implementation recommendation above.

## Verified follow-up

The registry and structural semantic gaps identified above now have executed cross-language coverage in `conformance-payload-result.json`: 21 test methods, including all ten registered payloads, valid signed bad-payload rejection, and all 21 preserved P00 semantic-negative fixtures plus duplicate/self-identity cases. Both SDKs now enforce the structural P00 cross-field rules. This supersedes the earlier shape-only observations for the updated candidate; it does not erase their role in finding the missing checks.

The first expanded run hit the unchanged 60-second subprocess bound while repeatedly scanning schemas through the WSL Windows mount. Its failed report is retained as `conformance-payload-before-mirror.json`. The runner now uses an exact-hash-verified temporary native copy, cleans it after use, and preserves every assertion and timeout. The failed selection then passed in 2.198 seconds, and the complete 21-test suite passed in 33.322 seconds. Fixture/evidence records bind the actual source and copied bytes; these timings are not production throughput claims.

Remaining work from this audit is principally the five promoted state models and executable transition/replay/deadline/cancellation/unknown-result histories, plus their connection to real-broker fault fixtures. Product enrollment, current-grant lookup and authority evaluation remain separate later owners. No P01 phase acceptance is asserted here.
