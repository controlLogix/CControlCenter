# Plain-language rules

Use these rules for every response and every piece of human-readable content you create or edit. They apply to chat, progress updates, questions, reports, plans, presentations, diagrams, UI messages, code comments, commit and pull-request descriptions, and prose, labels or explanations within generated data. Include these rules in delegated instructions when workers do not inherit them. Use plain English unless the user requests another language; apply the same clarity principles in that language.

## Reader outcomes

The rules use the four publicly documented principles of ISO 24495-1:2023. Write for the intended reader's knowledge, purpose and next action.

| Principle | Required outcome |
| --- | --- |
| Relevant | Answer the reader's actual question. Include the facts, context and limits needed for their decision. |
| Findable | Put the main answer first. Arrange details in a useful order and use descriptive labels and links. |
| Understandable | Use familiar words, direct sentences and consistent terms. Explain technical language when the reader needs it. |
| Usable | Make the action, responsible person, prerequisites and expected result clear when they matter. |

## Repository writing practices

These are our practical instructions for applying the principles, not quotations from ISO.

- Lead with the answer, outcome or requested action. Then explain the reason and supporting evidence.
- Prefer concrete words and active verbs. Name who does what when responsibility matters.
- Keep sentences and paragraphs focused. Remove repetition, filler, slogans, unexplained acronyms and unnecessary jargon.
- Define a necessary technical term on first use, then use it consistently. For example: "A materialized view is a stored copy used for queries."
- Explain what a technical detail means for the reader. Include examples when they make a task or distinction easier to understand.
- Use headings, lists, tables and diagrams when they help the reader find or compare information. Keep short answers simple.
- Preserve conditions, exceptions, units, sources and uncertainty. Distinguish a proposal from an implementation, a test result from an assumption, and worker completion from accepted work.
- For instructions, state the steps in order and explain how to check the result. For errors, explain what failed and the next useful action when known.
- Write respectful adult language. Plain language must retain the detail needed for accurate technical work.

## Code and structured data

Keep executable syntax, schema keys, enum values, protocol subjects, API names, paths, commands, formulas, units, recorded values and required formats exact. Do not rename or change them just to simplify wording. Write explanatory text, descriptions and display labels in plain language. Keep JSON, YAML, CSV and other requested formats valid; do not add prose outside a required machine-readable response. Preserve quotations and source evidence, with a separate explanation when useful.

## Review before delivery

Check silently whether the intended reader can find the answer, understand it correctly and act on it. Fix unclear wording without changing the facts. Use reasonable assumptions about the audience when possible instead of interrupting routine work. For important product documents and complex instructions, include feedback from representative readers in the existing review process. Sentence-length targets and readability scores are aids, not proof of clarity. Plain-language review does not replace accessibility checks.

## Basis and limits

Part 1 is the general plain-language standard, not an English-only standard.

This review used public ISO descriptions and accessible previews. It did not include the full purchased Part 1. These repository rules do not claim ISO certification or a complete conformity assessment. [Part 4 on organizational implementation](https://www.iso.org/standard/90061.html) remains a draft as of the review date and is not treated as a published requirement here.
